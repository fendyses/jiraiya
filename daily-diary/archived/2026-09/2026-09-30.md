## 2026-09-30 (Morning - 11:36 GMT+8) - NILAM PIC Resubmission Workflow Investigation and Fix

### Session Summary
- Type: Production diagnosis, bug fixing, regression testing, and commit preparation
- Focus: Investigate why applications 8387, 8438, and 9019 remained at Action Required after the PIC attempted to return them to the vetter following the missing-attachment update
- Outcome: The production states were verified read-only, the old and new return paths were unified behind guarded server-side rules, rollback cleanup and test isolation were hardened, all 45 tests passed, and the completed fix was committed to `development` as `45a1b53f`

### Main Topics Discussed
1. Inspected production data for applications 8387, 8438, and 9019 and confirmed that the first two were still returned to PIC with existing vetting documents and no PIC response, while 9019 had completed one return cycle before being returned again by the vetter.
2. Traced the regression to the September missing-attachment recovery feature: the new return endpoint handled only applications with no vetting documents, while applications with an existing draft continued through the older, less-protected document route.
3. Introduced one shared return-to-vetter eligibility check covering returned application status, PIC ownership, completed attachment recovery, assigned-draft document stage, and an assigned vetter.
4. Extended the guarded return transaction to support both no-draft recovery cases and existing vetting documents, including mandatory PIC feedback, stale/latest-document checks, duplicate-return prevention, and optional revised DOC/DOCX versions.
5. Prevented email failures from rolling back a successful workflow transition and ensured uploaded local or MinIO files are cleaned up when a later database operation fails.
6. Corrected the separate `VettingDocumentAlert` undefined `$who` failure with safe defaults and explicit handling for the new return title; the fix remains on `development` in commit `d13ba9b7` and was reverted from the local `puu_monitoring` branch as requested.
7. Fixed an outdated placeholder feature test and Telescope static-state leakage so the full suite runs reliably in sequence.
8. Removed the local Google-login switch from `config/services.php` before commit and cleared generated Blade views; only the eight intended application and regression-test files were committed.

### Key Insights & Learning
- The regression was not caused by the three application records themselves; it came from splitting the same business transition between a new no-document recovery route and the legacy existing-document route.
- A shared server-side eligibility rule is safer than controlling the workflow only through conditional buttons because cached forms and direct POST requests must obey the same constraints.
- Database rollback does not automatically remove files already moved to local storage or MinIO, so file cleanup must be treated as part of transaction failure handling.
- Full-suite ordering exposed Telescope callbacks that retained references to a flushed Laravel application; focused tests alone could not reveal that isolation problem.
