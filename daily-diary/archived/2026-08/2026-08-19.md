## 2026-08-19 (Morning - 10:54 AM) - Nilam: Approval Letter Missing Jawi/Hijri Images

🕐 10:54 GMT+8

### Session Summary
- Type: Work (UiTM — Nilam)
- Focus: `/meuapprovals/approved?meetingNo=162` — downloaded approval letter PDF showing "Image not found or type unknown" in place of several items
- Outcome: Root cause identified (outbound HTTPS fetch failing on production server, **not** an expired certificate), fixed in code by removing the network dependency entirely. Verified across the whole database and **committed by Fendy as `ed52517`** at 10:33.

### Main Topics Discussed
1. **Initial report** — Fendy downloaded `surat_approval_meu.pdf` and found broken-image placeholders, despite the image URLs opening fine in a browser. His hypothesis: expired SSL certificate.
2. **Traced the render path** — `MeuApprovalController@letter()` (line 306) renders via **dompdf** (`barryvdh/laravel-dompdf` v2.2.0 / `dompdf` v2.0.8). The letter body comes from `applications.meu_letter`, raw TinyMCE-authored HTML echoed unescaped into the Blade view. That HTML carries three absolute `https://` image URLs.
3. **Certificate check** — both certs valid: `*.uitm.edu.my` (nilams) to **2027-02-08**, `cdn.uitm.edu.my` (Sectigo) to **2026-08-24**. Not expired. Flagged the CDN one as expiring in 5 days regardless.
4. **Fendy pushed back twice** — server team said "SSL at server is OK", so maybe "the cert in this code needs updating". Rechecked properly rather than repeating myself.
5. **Ruled out every alternative** — searched the whole repo for any `.pem` / `cacert` / `CURLOPT_CAINFO` / `cafile` / `httpContext`: **none exist**. dompdf ships no CA store; it delegates to PHP's OpenSSL. Also cleared: `enable_remote` is `true`; no `allowedRemoteHosts`; no redirects (dompdf hard-defaults `follow_location => false`, so a redirect *would* have broken it); no WAF/User-Agent blocking (host runs Barracuda — tested dompdf's exact UA, browser UA, empty UA, all HTTP 200); all three files are valid non-interlaced 8-bit RGBA PNGs.
6. **Decisive test** — replicated dompdf's exact `Image\Cache::resolve_url()` path with the app's real config. All three images resolved cleanly locally, proving the code and config are correct and the failure is environmental on the production box.
7. **Identified what the broken images actually were** — read the PNGs directly: `bulan/02.png` = **صفر (Safar)**, the **Hijri month name**; `salam.png` = the Assalamualaikum greeting; `slogan.png` = UiTM's motto *Usaha, Taqwa, Mulia*. All **Jawi/Arabic script**, stored as images because dompdf's fonts can't render Jawi. The date line is `Tarikh : {{Y}}H <img bulan/NN.png> {{d}}` — year and day are text and always worked; only the month, being an image, failed.
8. **Fix implemented** — new `app/Traits/LetterImageHelper.php` rewrites `<img src>` in stored letter HTML to local copies at render time. Wired into 4 endpoints: `MeuApprovalController@letter`, `LpuApprovalController@letter`, `MyApplicationController@approvalLetter`, `MyApplicationController@lpuApprovalLetter`.
9. **Case report PDF** — generated a 4-page A4 RCA document at `~/Downloads/NILAMs_Letter_Image_Case_Report.pdf`, rendered with the project's own dompdf and embedding the actual Jawi graphics.

### Key Insights & Learning
- **"SSL on the server is OK" and "PHP can make outbound HTTPS calls" are different claims.** The team verified the *inbound* listener certificate (what browsers validate); dompdf depends on PHP's *outbound* CA trust store (`openssl.cafile`). Renewing the site cert does not touch it. This distinction was the crux of the whole back-and-forth.
- **There was never a certificate in the code to update.** Worth holding that line under repeated pushback — caving would have sent the team hunting a file that doesn't exist.
- **dompdf fails silently on image fetch.** It catches the warning, throws nothing, and substitutes placeholder text — so a letter still "generates" while missing content. Nothing surfaces in app logs.
- **The app was fetching its own static assets over the public internet.** TinyMCE stores `URL::asset()` output, which is absolute, so a locally-available PNG became a network round-trip. Removing that dependency killed the entire failure class (cert, WAF, DNS, timeout, outage) at once.
- **Reproducing the bug beat arguing about it.** Blocking dompdf's network locally gave `embedded images: 0` — the exact production symptom — and `6` after the fix. That single before/after was more convincing than any amount of cert inspection.

### Collaboration Highlights
- Fendy correctly refused to accept the first answer and pushed for a recheck. That was the right instinct — the recheck is what produced the `follow_location`/WAF/`resolve_url` evidence and turned a plausible theory into a proven one.
- Kept the diagnosis honest instead of agreeing with the "update the cert" framing, while still giving him something concrete and actionable to hand the server team.

## 2026-08-19 (Afternoon - 3:52 PM) - Nilam: LPU status display — a fix I got wrong twice before getting it right

🕐 15:52 GMT+8

### Session Summary
- Type: Debugging → wrong fix → self-correction → design discussion (UiTM — Nilam)
- Focus: `/lpuapprovals/drafted` — app 9022 listed as "LPU Notified" but its View page said "Approved by LPU"
- Outcome: Root cause was the **View page missing an intentional mask**, not the mask being wrong. Fixed in one line (`ba17f3d`). Two of my earlier attempts were wrong and were reverted. Ended in an open design discussion about a missing status.

### What happened, in order
1. **Diagnosed the mismatch.** Lists render `($row->lpu_approval == 1) ? applicationStatus->name : 'LPU Notified'`; `show.blade.php:56` rendered the raw status. Same app, two labels.
2. **First fix — WRONG.** I read the hardcoded `'LPU Notified'` as a display bug and stripped it from all 3 DataTables methods plus `index.blade.php`, making every page show the raw status. Found 147 apps at `lpu_approval=0` + status 14 and framed them as "mislabelled".
3. **Second error on top of it.** I used `$row->applicationStatus->name`, but the DataTables `->select()` never includes `application_status_id`, so the relation could not resolve — Fendy's screenshot came back with the **Status column completely blank**. Corrected to `$row->status`, the alias the query already joins.
4. **Alarm about "880 corrupted rows" — WRONG.** A DB-wide sweep showed 880 LPU-pipeline apps whose stored status disagreed with their own latest log. I reported this as data corruption.
5. **Fendy pushed back**: *"i did with your recommendation. you can check diary for this case."* Reading `daily-diary/archived/2026-07/` 07-23, 07-24 and 07-29 reversed the whole diagnosis.
6. **Reverted everything and fixed the actual bug** — added the same mask to `show.blade.php` instead.
7. **Fendy corrected my NULL handling.** I had "hardened" the check to exclude `NULL`; he asked whether NULL should count as notify. It should — I reverted to the plain list expression.
8. **Design discussion opened** (no code changed): why `/applications/9022` still says "Approved by LPU".

### The actual root cause (from the July diary, not from the code)
For notify-only apps (`lpu_approval = 0`), `LpuApprovalController::store()` **deliberately skips** the `application_status_id` update — only the `lpu_approval == 1` branch sets it. So their stored status legitimately freezes at 12 while the logs advance to 13/14. The 07-23 entry says it outright: *"Originally harmless because the app's real status field was left at 12 for notify apps."*

The `'LPU Notified'` string is the **intended companion** to that design: the stored status is meaningless for these apps, so the UI substitutes a fixed label. It looks exactly like a bug and is not one.

The June 2026 sync hook (`ApplicationStatusLog::created`) then created a *second* convention by forcing status to match each new log. Result, measured:

| `approved-by-lpu` log written | now at status 12 | now at status 14 |
|---|---|---|
| before hook (< 2026-06-05) | **878** | 9 |
| after hook (≥ 2026-06-05) | **1** (app 8860) | **138** |

So my "880 corrupted rows" were 878 rows in their **intended historical state**. Not corruption.

### Key Insights & Learning
- **Check the diary before "fixing" something that looks obviously wrong.** The answer had been written down on 2026-07-23 — including the exact sentence explaining the mask. I had even *quoted* that diary earlier in this same session while investigating the letter bug, and still didn't consult it before editing. `/recall nilam` first would have prevented every wrong step here.
- **Consistency with an existing convention beats a guard I invent.** My `!is_null(...) && == 0` "hardening" diverged from four places that all treat NULL as notify — `meeting()` line 369 routing, `meuapprovals/create.blade.php:130`, `rerouteLpuNotified()` (PHP `null == 0` is true), and every list. Fendy's simpler reading was correct.
- **A relation is not a substitute for a selected column.** `$row->applicationStatus->name` silently yields null when the FK isn't in the `->select()`. The join alias `$row->status` was already right there.
- **Backfill exonerated.** The SQL I recommended on 07-24 targeted `= 13`; app 8860 was at 14 by then, so it provably could not have been touched. Fendy did nothing wrong — 8860 stays a single unexplained row.

### The design discussion (open, nothing changed)
Fendy asked why `/applications/9022` shows "Approved by LPU", and whether that is the same thing as "LPU Notified". It is not. There are only four LPU statuses and **no terminal status for the notify path**:

| Stage | Approval path (flag 1) | Notify path (flag 0) |
|---|---|---|
| Entry | 11 Submitted for LPU Approval | 12 Submitted for LPU Notification |
| Middle | 13 Pending LPU Approval | *(none — correctly stays 12 post-`fcfc94a`)* |
| Exit | 14 Approved by LPU | **14 Approved by LPU — borrowed** |

Measured transitions confirm it: approval path runs `11→13` (55x) then `13→14` (64x); notify path historically ran `12→13` (2,219x — the old bug) then `13→14` (2,356x). Since `fcfc94a`, notify apps correctly hold at 12 (`12→12`, 37x).

So `store()` has the **same bug `meeting()` had, one stage later** — it hardcodes the approval terminal status for both paths. Proposed shape, mirroring the `meeting()` fix:
`$finalStatus = ($application->lpu_approval == 1) ? $approvedByLpu : $notifiedByLpu;`
That needs a new `notified-by-lpu` status, reassignment of the ~138 apps sitting at 14, and would make the mask unnecessary everywhere. Awaiting Fendy's answer on whether the LPU secretariat considers "notified" a genuinely distinct end state.
