## 2026-08-12 (Night - 10:33 PM) - MyStudent: Result Kolej Rayuan Leak Fix

🕐 22:33 GMT+8

### Session Summary
- Type: Work (UiTM — MyStudent)
- Focus: `/keputusan-kolej` — Rayuan results (RJ/RG) still showing to students even after the Rayuan flag was disabled
- Outcome: Root cause found, fixed, committed as `update fix rayuan leak`, and **deployed manually** (~22:55). Fendy had disabled the whole page as a stopgap; it can now be safely re-enabled with `rayuan_flag` off.

### Main Topics Discussed
1. **Complaint triage** — students with "Rayuan Berjaya / Gagal" results still appeared on the page despite Rayuan being turned off. Concrete case: student **2024514123**.
2. **Two-source model clarified** — Fendy questioned whether the flag comes from the API. Confirmed the page combines two sources: the *student record* comes from the myhep API (`/iresidensi/keputusan-permohonan-kolej`), while the *release flags/messages* (`rayuan_flag`, etc.) live in Firestore `mystudent/setting` → `result_kolej`, written by AdminPage.
3. **Root cause** — in `getResultCategory` (introduced by the 10-08 rewrite, commit `36193f5`), the intake-type check ran **before** the status check. A student with `INTAKE_TYPE` D/T/V and appeal status `RJ`/`RG` was classified as **penerapan**, so it was gated by `penerapan_flag` (on) and never consulted `rayuan_flag` (off) → the leak.
4. **Real payload confirmed the diagnosis** — Fendy pulled the API JSON for 2024514123: `STATUS: "RJ"`, `INTAKE_TYPE: "T"`, `STUDENT_RESULT: "PERMOHONAN RAYUAN KOLEJ BERJAYA"`. `INTAKE_TYPE "T"` matched the D/T/V list before `STATUS` was ever read.
5. **Postman walkthrough** — explained how to reproduce: borrow the myhep Bearer token from the logged-in app's localStorage (`token` key) and `GET` the endpoint; or two-hop via `verify-token`. Also noted the endpoint returns only the signed-in student's own record.
6. **Whitespace misread cleared up** — Fendy asked if the bug was whitespace. Clarified: no, the bug was purely the **order of the two checks**; the added `.trim()` is just defensive and unrelated to his clean `RJ`/`T` data.

### Key Insights & Learning
- **`STATUS` is the reliable signal; `STUDENT_RESULT` is only a display label.** Keying classification off `STATUS.startsWith('R')` is correct — every appeal (RJ/RG/bare R) begins with R.
- **Check order matters when categories overlap.** An appeal student can also carry a D/T/V intake type; the more specific signal (appeal status) must be tested first.
- The fix: swap the order so `status.startsWith('R')` → `rayuan` is checked before the D/T/V → `penerapan` branch. Verified with an 11-case truth table (all pass) and lint-clean.
- The gate uses `!== true`, so a category shows only when its flag is explicitly `true` — re-enabling the page won't accidentally expose appeals while `rayuan_flag` stays false.

### Looking Forward
- ✅ Build **deployed manually** (~22:55) — fix is now live.
- Re-enable the page (`flag: true`) and keep `rayuan_flag: false` until appeals are officially released.
- Possible future work: plain `Gagal` (`STATUS "G"`, no R prefix) still classifies as kemasukan — no separate flag exists to hide failed non-appeal results. Add a fourth flag only if that separation is ever needed.
