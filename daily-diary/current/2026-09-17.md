### Key Insights & Learning
- **The pencil icon in an application's Partners table is a global edit.** It opens `partners.modal.edit` and saves the shared row. The per-application swap lives on the Manage Legal Documents *listing* (green Edit Partner button, Admin-only), not on the show page. Two buttons that both say "edit partner" doing very different things is the root cause here, not the admin.
- **Pivot rows are an accidental backup.** `application_partner` snapshots contact person/email/phones at attach time. That's what let the SEDA contact be restored with confidence; the address wasn't snapshotted, so it wasn't.
- **Unique validation order matters when renaming in a swap.** Rename the wrong record away first, then create the right one. Otherwise MySQL's case-insensitive unique index blocks you.
- **`reference_no` is denormalised and only refreshed in two code paths.** Any new partner-changing UI (the Manage Partners modal is one) silently leaves it stale. Worth a code fix: regenerate on attach when the application has exactly one partner.

- Outcome: Root-cause path identified in code, live reproduction blocked pending the father's IC and the graduate's email. Notice shipped as a boxed info card and committed by Fendy as `0c67ed5`.

### Main Topics Discussed

1. **The `/attendance` "Semak" flow and its API.** The check button in `attendance.component.ts` calls `GET https://api.uitm.edu.my/alumni/semakV2?nokp=<IC>&email=<graduate email>` with a bearer token hardcoded in the component. Decoded the JWT: issued by `integrasi.uitm.edu.my` to staff 261852 (Mohd Azrul Amir), scope `/alumnai /alumni`, expires 26 Sep 2027. This is a different token from the `alumnai` one in `alumni-api.service.ts`, which only covers `fastapi.uitm.edu.my`.

2. **How a null gets saved.** The component reads `alumni`, `registered`, `alumni_id`, `name`, `salutation` from the response and patches `father_alumni_id` straight from `response.data.alumni_id`. There is no null guard and the control has no `Validators.required`. So if semakV2 answers `alumni:'y', registered:'y', alumni_id:null`, the name fills in, the read-only Alumni ID box shows blank, and `updateConvoNoFile()` writes null to Firestore without complaint. The "not found" branch would leave an empty string, not null, so the null points at the first branch.

3. **What impersonation does and doesn't prove.** Fendy impersonated the father and everything looked fine. That only exercises the father's own Firestore profile through `/impersonate`; it never hits semakV2. The graduate-side check depends on integrasi's mapping from the typed IC to an alumni_id, which is a separate data source.

4. **Reproduction attempts.** `fastapi.uitm.edu.my/alumnai/semak/id/1298578` confirms the father exists (Diploma Pentadbiran Awam, Shah Alam, 1994–1997) but returns no nokp or email, so the lookup can't be chained. Firestore REST read of `graduates/1335627` failed: gcloud needs a fresh `gcloud auth login`. Firebase CLI 15.20 has no `firestore:get`. Asked Fendy for the father's nokp and the graduate's login email to run the exact request.

5. **Borang Jubah notice on `/convocation`.** Added a note under the Muat Turun Surat Jemputan / Pengesahan Kehadiran / Borang Jubah button row: "Borang Jubah akan dijana setiap 2 jam selepas graduan membuat pengesahan kehadiran." First version was plain grey centred text matching the timezone line; Fendy asked for a box, so it became a `bg-light-primary` mat-card with a circle-info icon, the same pattern the attendance page uses for notices. Shown only when `convocation.pengesahan_kehadiran` is on. Dev build passes. Fendy committed it himself as `0c67ed5 update pemakluman borang jubah`.

### Key Insights & Learning
- **semakV2's `alumni_id` can be null while `registered` is `'y'`,** and the frontend trusts it blindly. A guard (treat missing id as not-found) plus a required validator on `father_alumni_id` / `mother_alumni_id` when the parent is marked alumni would stop the silent null.
- **Two different bearer tokens ship in the public bundle** — the integrasi one in `attendance.component.ts` and the alumnai one in `alumni-api.service.ts`. Still the same security debt noted on 14 Sep.
- **Impersonation is a Firestore-only view.** It is not a way to test integrasi lookups.
- **"save-diary" means the JIRAIYA protocol,** not an ad-hoc file. I first created a `DIARY.md` in the alumni repo and a wrong memory note; both removed this session.
