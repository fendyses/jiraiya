## 2026-08-20 (Afternoon - 🕐 16:15 GMT+8) - Tracing the Student Photo Pipeline in MyStudent

### Session Summary
- Type: Work (UiTM — MyStudent / mystudentvue)
- Focus: Answer a single investigative question — where does the app get the student image it displays?
- Outcome: Two distinct image pipelines identified and mapped end to end. Read-only session; no code changed, working tree clean.

### Main Topics Discussed

1. **The profile avatar — `currentUser.picture`**
   - Not Firebase Storage, and not fetched by any dedicated image call. It is a plain URL field on the student's Firestore document.
   - Source: `pelajar/{studentid}@student.uitm.edu.my` → field `picture`.
   - Read exactly once, at login: `src/services/auth.service.js:44` (`getDocWithRetry`), then the whole document is cached via `localStorage.setItem('user', ...)` at line 56.
   - Hydrated into Vuex at boot by `src/store/auth.modules.js:7`, which reads that localStorage blob into `state.auth.user`.
   - Rendered from the store in roughly fifteen places — `HomePage.vue:48`, `ProfilePage.vue:17`, `iResidensi.vue:10`, `kesihatan/KesehatanPage.vue:10`, `masmed2u/HomePageMasmed.vue:11` via `currentUser.picture`; `VirtualCard.vue:16`, `ResultPage.vue:21`, `ResultKolejPage.vue:32` via `this.$store.state.auth.user.picture`; `HeaderBar.vue:194` and `SidebarMenu.vue:140` copy it into a local `picture` data prop.

2. **Nothing in the repo ever writes `picture`**
   - Grepped every assignment site — the field is populated upstream (card/SIMS sync into Firestore), never by this SPA.
   - Confirmed by the blocking message at `HomePage.vue:322`: when the `Gambar` requirement is unmet, students are told to update it at `https://kad.uitm.edu.my`.

3. **The medical-form photo — a completely separate pipeline**
   - `src/views/kesihatan/MedicalForm.vue`: reads field `medicalform` off the same `pelajar/{studentId}@student.uitm.edu.my` doc (line 280), displays it at line 99.
   - Upload goes to `POST https://api.uitm.edu.my/convid19/cdn/upload/medicalform` with a Bearer token (line 530); the returned `result.url` is written back to the same Firestore doc by `saveToFirebase` (line 548).

4. **Unrelated image fields noted for completeness**
   - `TKS.vue` passport/business photos, `VotingPage.vue` `calon.photo`, `AktivitiPage.vue` `data.gambar` — each its own URL field from its own collection, not part of the student-identity photo path.

### Key Insights & Learning
- The avatar is a **login-time snapshot**, not a live read. Because the entire `pelajar` document is frozen into localStorage during `AuthService.login()`, a photo updated at `kad.uitm.edu.my` will not appear until the student logs in again. That is the practical consequence worth remembering the next time someone reports "my photo is still the old one".
- The `pelajar` document is doing double duty as both the identity record and a general per-student key/value store (`picture`, `medicalform`, height/weight/BMI, disease list). Handy, but it means "where does this image come from" has more than one answer depending on which image is meant.
- Firebase Storage is not used for any student imagery in this app — every image is an external URL (kad.uitm.edu.my for identity, api.uitm.edu.my CDN for medical form).

### Collaboration Highlights
- Fendy asked a tightly scoped question and got a tightly scoped answer: file paths and line numbers, both pipelines, plus the upstream origin — no speculative refactoring proposed on a read-only ask.

### Growth and Development Notes
- Reinforces the mental model built during the 2026-06 login-loop work: the `pelajar` doc → localStorage → Vuex chain is the spine of this app, and most "stale data" symptoms trace back to that single login-time snapshot rather than to any individual feature.

### Memorable Moments
- The answer to "where is the student image" turned out not to be a storage bucket at all, but a URL string that arrived once at login and has been sitting in localStorage ever since.

### Looking Forward
- If stale avatars ever become a real complaint, the fix is a targeted re-read of the `picture` field on app boot rather than a full re-login — worth scoping only if it is actually reported.
- No pending code changes from this session; the repo remains at `8fd446e update fix rayuan leak`, working tree clean.

## 2026-08-20 (Evening - 5:33 PM) - Nilam: Renewal Dates Surfaced, and a Certificate That Broke the Jawi Calendar

### Session Summary
- Type: Work
- Focus: Nilam — three interlocking investigations (missing renewal button, missing Jawi date image, silently renamed document) that each ended in a different root cause, plus a shipped feature and two written reports
- Outcome: 1 commit merged (`c85e5e3`), 2 PDFs written to jiraiya, PUU Monitoring prod requirements mapped

### Main Topics Discussed

1. **Why the "Apply Extension/Renewal" button was missing on application 4427**
   - `resources/views/myapplications/_actions.blade.php:31-36` gates it on `status == 'executed-document'` **and** `document_categories.duration == 1`. Category passed; status was `submit-for-meu-approval`, so the gate failed.
   - The partial is only rendered in the **listing** Actions dropdown, never on the detail page — so looking at `/myapplications/4427` would never show it regardless of status.
   - Second, later blocker found: `MyApplicationController@extension:506-517` requires at least one Activity with status `verified`. Application 4427 has **zero** activity rows.
   - Wrote the finding up in Bahasa Melayu for the PIC (DOCX + PDF via LibreOffice), moved both to `~/Downloads`.

2. **The Jawi Hijri month missing from generated MEU approval letters**
   - The month is not text — it is a PNG per Hijri month at `public/assets/images/bulan/01–12.png`, referenced by `URL::asset()` and **frozen into `tbl_applications.meu_letter` at draft time**.
   - dompdf must fetch it over HTTPS at render time; the placeholder string "Image not found or type unknown" comes from `vendor/dompdf/dompdf/src/Image/Cache.php`.
   - Ruled out in order: stored-URL corruption (scanned all 8,081 `<img>` refs across every letter — only the two correct hosts), `enable_remote`, `allow_url_fopen`, WAF user-agent blocking (empty/browser/PHP UA all returned 200), and general outbound blocking.
   - Decisive evidence came from the production PDF itself: matched embedded image XObjects by pixel dimensions — letterhead (788×138, local disk) ✅, `cdn.uitm.edu.my` slogan (314×50) ✅, but both `nilams.uitm.edu.my` images (189×55 and 1000×50) **missing**.
   - **Root cause found in the certificate**: `nilams.uitm.edu.my` was reissued **27 July 2026** onto **SSL.com TLS RSA Root CA 2022**, while `cdn.uitm.edu.my` stays on Sectigo → USERTrust (root from 2010). Server is Apache/2.4.41 = Ubuntu 20.04. dompdf fetches via `file_get_contents` (`Helpers.php:908`), so it validates against PHP's openssl store — which almost certainly predates the 2022 root.
   - This explained every symptom including "it worked before" and "the image loads fine in my browser".
   - Incident report written to `jiraiya/docs/reports/incidents/NILAM-TLS-CA-Incident-Report-Letter-Images.pdf` (7 pages) for the server admin, with read-only confirmation commands and a "ruled out" table to pre-empt deflection.

3. **The document that renamed itself**
   - Fendy noticed my BM report used the proper agreement title while the system showed `OFFER LETTER HCSB_signed`. My error — I had pulled the title from the `application_renews` snapshot, not the live row. But it surfaced a real rename.
   - Window pinned: after **2024-09-04** (snapshot still correct) and at/before **2025-03-13** (last write). No field-level audit exists — only status logs.
   - Ruled out the renewal flow: of 25 renewed records, **22 kept their names**.
   - Ruled out Nurhidayah (user 196) despite her `updated_by` stamp: her 13 March batch touched 20+ applications in 45 minutes and **none of the others were renamed**; `ApplicationPolicy::update` returns false for her on 4427 (PIC/Applicant branch, not a listed PIC nor creator); and every mass-assign path is `authorize('update')`-guarded.
   - **Likely accidental mechanism identified**: `changeFile()` auto-fills the document-name box from the uploaded filename — `fileName.replace(/\W+/g, " ")` preserves underscores, producing exactly `OFFER LETTER HCSB_signed`. Those inputs ship as bare `name="name"` and rely on jquery-repeater renaming them to `maindocuments[0][name]` in the browser. If that rewrite doesn't run, a scalar `name` posts and mass-assignment overwrites `applications.name` — while the upload is silently dropped, which matches the absence of any document row bearing that name.

4. **Renewal periods were invisible system-wide — and shipped a fix**
   - `storeExtension` posts `ext_st_date`/`ext_exp_date`, neither of which is in `Application::$fillable`, so `aggmt_st_date`/`aggmt_exp_date` are never updated. **22 of 25 renewed agreements display a pre-renewal expiry.**
   - The intended destination columns (`aggmt_renewal_*`, `aggmt_extend_*`) are in `$fillable` but **do not exist in the database** — migration never written.
   - Grepped every Blade template: **no view reads `tbl_extensions` at all**.
   - Also found the snapshot dates are off by one day in 22 of 25 rows — `toArray()` serialises Carbon to UTC and `Asia/Kuala_Lumpur` midnight becomes 16:00 the previous day.
   - Built `extensions()` + `latestExtension()` + `expiryDateHtml()` + `durationHtml()` on the model and applied them across **13 controllers (17 render sites) and 3 detail views**. Non-renewed records render byte-identical to before. Registered 5 expiry columns in `rawColumns` (without which the markup would have been escaped), eager-loaded `extensions` on every affected query, and measured **0 extra queries across 25 rows**.

5. **Git hygiene and the merge**
   - Staged only the feature — `Application.php` also carried the PUU `scopeVisibleTo()` scope, so split the file by hunk and used `git apply --cached` to stage mine alone. Verified the staged diff contained zero PUU references.
   - Committed `c85e5e3`, then discovered we were 2 behind and merged `origin/development` cleanly (no conflicts — incoming hunks at lines 26/306/1496 never touched mine at 53–299).
   - Incoming `ed52517` added a `LetterImageHelper` trait that rewrites letter `<img>` tags to local paths in memory — a **better fix than the base64 approach I had proposed**, since it repairs all existing letters rather than only newly drafted ones.

6. **PUU Monitoring menu invisible — and the reason was environmental**
   - All five permissions missing from prod; the sidebar wraps the whole section in a `hasAnyPermission` gate, so even the ungated "Work Monitoring" link disappears.
   - Fendy remembered the cause himself: he had switched from the dev DB to the prod DB.
   - Audited prod: 2 tables, 2 indexes and 5 permissions all missing; all four target roles already exist.
   - Wrote `jiraiya/docs/reports/deployments/NILAM-PUU-Monitoring-Production-Install.pdf` (6 pages) — DDL, permission→role matrix, config values, install order, verification queries, rollback.

### Key Insights & Learning
- **The most useful evidence was in the artefact, not the code.** Decompressing the production PDF and matching embedded images by pixel dimensions identified precisely which two fetches failed — that single measurement collapsed a five-way hypothesis space to one.
- **My own mistake became the lead.** Quoting the snapshot title instead of the live one was wrong, but it exposed a rename nobody had noticed. Worth remembering that a mismatch between a report and a screen is itself a finding.
- **"It worked before" reframed everything.** I had a coherent explanation (server can't reach its own hostname) that fit all the evidence until that sentence arrived — then the certificate dates showed the two hosts sit on different CAs and the earlier inference collapsed. Cheap to check, and it was the whole answer.
- **Absence of a record can be confirming rather than exculpatory.** I first read "no document row with that name" as evidence *against* a form leak; it is actually exactly what that failure mode produces, because the repeater failing means the document array never arrives at all.
