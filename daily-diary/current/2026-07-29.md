### Main Topics Discussed
1. **Two different LPU letters — do not confuse them.**
   - `lpu_email` = "Pemakluman Awal" preliminary letter, edited at `/lpuapprovals/create?id={id}`, sent by `store()` via `LPUMail`.
   - `lpu_letter` = the LPU **approval** letter, edited at `/lpuapprovals/letter/{id}/edit`, downloaded as `surat_approval_lpu.pdf`.
   - Both PDFs render **on the fly** from the HTML column — no file is stored, so any later edit retroactively changes what the applicant downloads.
2. **Can she edit after submitting?** Not via the UI — `show.blade.php:215` drops into an `@else` branch offering only Download once both fields are filled. The "Edit Letter" button at `:227` is **dead code** (its `@if`/`@elseif` at `:219`/`:221` are exhaustive, so the `@else` never renders). But `editLetter()` and `update()` have **no guards at all** — only `auth` middleware, no role check — so the direct URL still opens the editor and overwrites the column at any stage.
3. **"Save as Draft" is the only save**, and the label lies: it writes straight to the live column, not a draft copy. "Download Letter" is a plain `<a href>` that renders the **last saved** version, so editing then downloading without saving shows stale content and looks like the edit failed.

### Key Insights & Learning
- **The backfill's `WHERE` clause is why these 9 survived.** The 88-row correction targeted `lpu_approval = 0 AND status = 13`. By the time it ran, these 9 had `lpu_approval = 1` and had moved to status 14/16 on 27 Jul — matching neither condition. Swept all 132 active meeting-#29 rows: **0** still match the original damage signature, and exactly **9** have the remaining conflict (flag = 1 but history contains a `submit-for-lpu-notified` log). Nothing else in the meeting is inconsistent.
- **Nilam has no column-level audit trail.** `application_status_logs` records status changes only. A pre-27-Jul export proves `lpu_approval` was 0 for these 9 (the page renders the hardcoded "LPU Notified" only when the flag is 0), yet it is 1 now — and the 17 Jul bug never touched that column. Ruled out a legitimate reroute: `rerouteLpuApproval()` writes a status-11 log and none of the 9 has one. So the flag was changed directly, by an unknown hand.
- **Re-sending costs a workflow rollback.** `store()` sets `application_status_id` back to 14, so an app at 16 (Signatory Nomination Setup) is knocked backwards and signatory nomination has to be redone. App 8732's own history proves it: `16:07 approved → 16:09 signatory → 16:40 approved → 17:16 signatory` on 27 Jul.
- **`/lpuapprovals/pending` excludes anything with `lpu_email` set** (`whereNull('lpu_email')`), which is why the 9 weren't there and the "LPU Notified" the user saw on that page belonged to 101 *other*, genuinely notify-only apps. Their correct home is `/lpuapprovals/drafted`, where meeting 29 is the default selection.
- **There is no "LPU Approved" label, by design.** The rule is `lpu_approval == 1 ? applicationStatus->name : 'LPU Notified'` — notify apps get a fixed cosmetic string, approval apps show their real status. Status 14 "Approved by LPU" is the genuine counterpart.
- **The approval-letter step is never enforced.** Sending the preliminary email alone logs `approved-by-lpu` and pushes the document to `signing-document`, so an app can advance with `lpu_letter` still NULL — which is exactly what happened to all 9.
- Tooling: **PyMuPDF (`fitz`)** again the only working PDF path on this Mac (`pdftoppm` absent). Production DB needs the UiTM **VPN** on.
